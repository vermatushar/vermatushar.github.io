Synapse: Unified Agent Runtime, Online Evaluations & Observability

09 April 2026 · Tushar Verma
Agent Runtime Online Evaluations Observability Multi-Agent Systems

The agent ecosystem has a reliability problem. Not because models are bad at reasoning — they've gotten remarkably good. The problem is that the infrastructure between the model and the world is held together with duct tape. Prompt chains break silently. Tool calls fail without telemetry. Evaluations happen offline, days after a regression ships. And when something goes wrong in production, the debugging story is "grep through logs and pray."

Synapse is my attempt at fixing this — an open agent runtime that treats evaluation and observability as first-class primitives, not afterthoughts bolted onto an orchestration framework. The thesis is simple: the runtime layer is the right place to solve agent reliability, because the runtime is the only layer that sees everything.

The Problem with Today's Agent Stack

Most agent frameworks today — LangChain, CrewAI, AutoGen — focus on the happy path: define agents, wire them together, ship. The abstraction they offer is orchestration. But orchestration is a solved problem. What's unsolved is what happens when agents don't work, which is most of the time.

Here's what I've seen break repeatedly in production agent systems:

  • Silent tool failures. An agent calls an API that returns a 429. The framework retries, gets a different error, and the agent hallucinates a response. Nobody notices for three days.
  • Context contamination. Agent A's conversation state leaks into Agent B because they share a memory store without proper isolation. The system "works" but produces subtly wrong outputs.
  • Evaluation drift. The team runs evals weekly on a golden dataset. But the prompts changed on Tuesday, the tool schemas changed on Thursday, and the evals on Friday are testing a system that no longer exists.
  • Unobservable agent reasoning. An orchestrator spawns four sub-agents in parallel. One of them makes a bad tool call that cascades. The only log is "task failed." Good luck debugging that at 2am.

These aren't edge cases. They're the default experience of running agents in production. The common response is to build custom monitoring on top of whatever framework you're using. But that's solving the symptom, not the disease.

Why the Runtime Layer

A runtime sits between the agent logic and the outside world — it manages execution, tool dispatch, memory, and inter-agent communication. This position gives it a unique vantage point: the runtime sees every input, every output, every tool call, every state transition, and every failure. No other layer in the stack has this visibility.

This is why I believe the runtime is where evaluation and observability belong. Not as plugins. Not as middleware. As core primitives that the runtime guarantees.

Think of it like this: you wouldn't bolt error handling onto a programming language as a library. You build it into the runtime (try/catch, Result types, panic handlers). Agent reliability deserves the same treatment.

Synapse Architecture

Synapse is designed around three pillars: execution, evaluation, and observability. They share the same data model and trace format, so they're not three systems stitched together — they're one system with three faces.

1. Execution: Gateway-Based Agent Harness

At the core of Synapse is a gateway-based execution model. Every agent runs in an isolated context — its own memory scope, its own tool namespace, its own model routing configuration. The gateway manages:

  • Context isolation. Each agent gets a scoped workspace. No shared mutable state unless explicitly configured. This eliminates an entire class of contamination bugs.
  • Tool dispatch. Tools are exposed as single-purpose MCP servers. The runtime handles protocol negotiation, auth, rate limiting, and failure modes. Agents declare what tools they need; the runtime provides them.
  • Workflow orchestration. Deterministic YAML workflows define how agents compose — sequential, parallel, conditional branching, subagent spawning. The workflow engine handles inter-agent state handoff with explicit schema contracts.
  • Model routing. Different agents can use different models. The gateway routes each agent's inference calls to the appropriate model endpoint, with fallback chains and cost budgets.

The key design decision is that agents are composable but isolated. You can build a complex multi-agent system where each agent is independently testable, replaceable, and observable. The gateway is the single point of control.

2. Online Evaluation Pipelines

This is where Synapse diverges most from existing frameworks. Traditional agent evaluation looks like this:

  1. Collect a dataset of inputs and expected outputs
  2. Run your agent on the dataset
  3. Score the outputs
  4. Write a report
  5. Realize the report is stale by the time anyone reads it

Synapse's approach is different. Evaluations run continuously, inline with production traffic. Here's how:

Trace-based eval triggers. Every agent execution produces a structured trace. Eval pipelines subscribe to these traces in real-time. When a trace matches a trigger condition (e.g., "this agent called the database tool"), the eval pipeline fires.

Evaluator calibration. Automated evaluators (LLM-as-judge, rule-based checkers, embedding similarity) are calibrated against human annotations using a reference dataset. The calibration score is tracked over time. If an evaluator's agreement with humans drops below a threshold, it gets flagged.

Regression detection. Eval scores are tracked per-agent, per-tool, per-workflow. When a score drops below its rolling baseline, the system triggers an alert with the specific traces that caused the regression. No more "evals are red, figure out why."

Shadow evaluation. You can run a new prompt or agent configuration in shadow mode — it sees real production inputs but doesn't affect outputs. The eval pipeline scores both the production and shadow paths, giving you a direct A/B comparison before you ship.

The goal is to make evaluation a continuous feedback loop, not a periodic checkpoint. When you change a prompt, you know within minutes whether it helped or hurt — not days.

3. Trace-Level Observability

Every agent execution in Synapse produces a structured trace — a tree of spans that captures the full execution path. This isn't just logging. It's a semantic representation of what the agent did, why, and what happened.

A trace captures:

  • Agent reasoning steps — the model's chain-of-thought, tool selection rationale, and decision points
  • Tool calls — request, response, latency, error state, retry count
  • State transitions — memory reads/writes, context window changes, workflow branching decisions
  • Inter-agent communication — handoff payloads, spawned subagent traces (nested as child spans)
  • Evaluation results — inline eval scores attached to the relevant span

Traces are the unifying data model. Evals consume traces. Dashboards render traces. Alerts fire on trace patterns. Debugging starts with a trace ID and drills down. Everything is connected because everything speaks the same format.

This is heavily inspired by distributed tracing in traditional systems (Jaeger, Zipkin, OpenTelemetry), adapted for the specific semantics of agent execution. The key difference is that agent traces are semantic, not just temporal — they capture what the agent was trying to do, not just what functions it called.

Design Decisions and Trade-offs

YAML Workflows vs. Code-Defined Graphs

Synapse uses declarative YAML for workflow orchestration. This is a deliberate choice. Code-defined agent graphs (like LangGraph) are more flexible, but they're harder to version, harder to validate statically, and harder to visualize. YAML workflows can be linted, diffed, and rendered as DAGs. The trade-off is expressiveness — you can't embed arbitrary logic in a YAML node. But I've found that most multi-agent workflows are structurally simple (sequence, parallel fan-out, conditional routing). The complex logic lives inside agents, not between them.

MCP as the Tool Protocol

Every tool integration in Synapse is an MCP server. MCP (Model Context Protocol) gives us a standard interface for tool discovery, invocation, and authentication. This means tools are hot-swappable, versionable, and testable in isolation. The downside is protocol overhead — an MCP call is heavier than a direct function call. But for production agent systems, the observability and isolation benefits far outweigh the latency cost.

Online Evals vs. Offline Evals

Synapse doesn't replace offline evaluation — you should still run comprehensive evals on golden datasets before deploying. But offline evals have a fundamental limitation: they test the system as it was, not as it is. Online evals close that gap. The trade-off is compute cost. Running evaluators on every trace is expensive. Synapse handles this with sampling — you can configure what percentage of traces get evaluated, with smart sampling that over-indexes on novel patterns and error states.

What I'm Building Next

Synapse is still early. The execution layer is stable and I've been using it internally for agent systems at work. The eval and observability layers are in active development. Here's what's on the roadmap:

  • Eval DSL. A lightweight domain-specific language for defining evaluation criteria that's more expressive than config but less heavyweight than Python scripts.
  • Trace replay. The ability to replay a production trace with modified agent configurations — essentially time-travel debugging for agents.
  • Cost attribution. Per-agent, per-tool cost tracking that ties back to traces. Know exactly which agent in which workflow is burning your inference budget.
  • Community evaluators. A registry of reusable eval modules (hallucination detection, tool-use accuracy, instruction following) that plug into the pipeline.

Closing Thoughts

The agent ecosystem is at an inflection point. We've proven that LLMs can reason, use tools, and coordinate. The next bottleneck isn't capability — it's reliability. And reliability is an infrastructure problem, not a model problem.

Synapse is my bet that the right abstraction is a runtime that treats evaluation and observability as first-class concerns. Not because existing frameworks are bad, but because they were designed for a world where the hard part was getting agents to work at all. Now that agents work, the hard part is knowing when they don't — and fixing it fast.
